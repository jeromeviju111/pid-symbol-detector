# P&ID Symbol Detector

Detects symbols, tags, pipe lines, and connectivity in Piping &
Instrumentation Diagrams (P&IDs), with a human-verification layer and an
LLM-powered Q&A interface over the extracted data.

## What it does

```
P&ID image/PDF
      |
      v
YOLO symbol detection (best.pt)
      |
      v
OCR tag matching (EasyOCR)
      |
      v
Check SQL corrections  ---->  apply any human-verified overrides
      |                       for this document
      v
Corrected symbol list
      |
      v
Line detection (OpenCV) + Arrow detection
      |
      v
Connectivity graph (pixel flood-fill between symbols)
      |
      v
Diagram graph  ---->  Gradio UI  /  LLM Q&A
```

`best.pt` is never modified. Human corrections are stored separately in
`corrections.db` and re-applied on top of fresh model output every time a
document is processed — see **Correction persistence** below.

## Features

- **Full Detection** — view detected symbols, text, lines, arrows, or all
  combined, plus a symbol-count table.
- **Symbol Matcher** — click a symbol, find every symbol of the same class
  across all pages of the document.
- **Manual Verification** — correct a wrong class, delete a false
  positive, add a symbol the model missed, or restore a symbol to its
  original YOLO prediction. Corrections and additions persist to
  `corrections.db` and reapply automatically next time this document is
  processed.
- **Asset Hierarchy** — click a symbol, see what it's connected to
  (traced via the connectivity graph).
- **Ask the Diagram** — chat interface over the extracted structured
  data (not the raw image). "How many X" questions are answered
  directly from computed counts, bypassing the LLM. Supports a local
  Ollama backend (free) or a hosted OpenRouter backend (paid).

## Setup

### 1. Install dependencies

```bash
pip install -r requirements.txt
```

### 2. Set up an LLM backend for "Ask the Diagram" (optional — everything
else works without this)

**Ollama (local, free) — primary backend:**
```bash
ollama serve
ollama pull llama3.1   # or whichever model you want to use
```

**OpenRouter (hosted, paid per token) — backup, if Ollama isn't
available or a heavier hosted model is needed:**
```bash
export OPENROUTER_API_KEY=sk-or-...   # get one at openrouter.ai/keys
```
Pick "OpenRouter (hosted, paid)" from the backend dropdown in the app
when you want to use it instead of Ollama.

### 3. Run the app

```bash
python app.py
```


## Correction persistence

Corrections and manual additions are keyed by `(document, tag,
position)`, not just tag — a nearby OCR-read label isn't always a
unique instrument tag (e.g. a generic caption like "Instrument Air
Supply" can sit next to more than one symbol), so position disambiguates
symbols that would otherwise collide on the same key. `document` is
derived from the uploaded filename, so:

- Re-uploading the **same** file reapplies saved corrections automatically.
- A **different** file is never affected by another document's corrections.

`corrections.db` is gitignored deliberately — it's local runtime data,
not source. Each person processing documents locally will accumulate
their own; it isn't meant to be merged between teammates via git.

## Evaluation metrics

`symbol_evaluation_metrics_full.csv` — per-class precision, recall, and
mAP@50 for `best.pt`, generated by `evaluate_pipeline.py` against
`data.yaml`'s validation set. This is the concrete data behind the
"symbol detection is not 100% accurate" limitation above — some classes
detect reliably, others (lower precision/recall) are more likely to be
missed or misclassified, which is exactly where the correction system
matters most.

To regenerate it: `evaluate_pipeline.py` currently has `MODEL_PATH` and
`DATA_YAML` hardcoded near the bottom of the file (as absolute paths
from whoever last ran it) — edit those two lines to point at your own
local `models/best.pt` and `data.yaml` first, then run:

```bash
python evaluate_pipeline.py
```

## Known limitations

- Symbol detection is not 100% accurate. Because line tracing, arrow
  detection, and connectivity all depend on the symbol list, a missed
  or misclassified symbol can produce an incomplete or incorrect flow
  path for that section of piping, not just one wrong label.
- Position-bucket correction matching assumes the document renders at
  the same resolution on every run.
- `corrections.db` is local-only; deploying this app somewhere with an
  ephemeral filesystem (e.g. free-tier Hugging Face Spaces) will lose
  it on every restart unless backed by persistent/external storage.
- Manual corrections don't retrain `best.pt` — they're an override
  layer, not a model improvement. `corrections_db.list_corrections()`
  provides an audit trail that could seed a future retraining set.
